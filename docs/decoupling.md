# Слоты как отдельные компоненты

Цель: поменять TTS, мозг или Telegram **и не открывать** репозитории остальных слотов. Чужой код меняется только если меняется сам контракт — и это должно быть редко, явно и с новой версией протокола.

Сейчас в `src/` это ещё не так: runtime импортирует провайдеры напрямую. Ниже — как сделать правильно, и почему «отдельный репозиторий» само по себе проблему не решает.

## Что на самом деле должно быть независимым

Не папка и не git. **Процесс + контракт.**

```
echo-tts            echo-llm           echo-memory
   процесс             процесс            процесс
      \                   |                  /
       \                  |                 /
        +-------------- echo.v1 -----------+
                          |
                    echo-runtime
                          |
                    echo-channel
```

Runtime **не импортирует** код слота. Он запускает процесс или стучится в URL и говорит на `echo.v1`. Слот не импортирует runtime и не импортирует соседний слот.

Если Zonos меняешь на XTTS — правишь только `echo-tts` (или его адаптер). Runtime, llm, память, каналы даже не пересобираются.

Если хочешь, чтобы слоты звали друг друга напрямую (`tts` ходит в `identity` за голосом) — независимость сразу мёртвая. Поэтому контекст **едет в конверте**, а не добывается запросом к соседу.

## Одно общее, всё остальное — нет

Единственная общая зависимость: **протокол**.

| Можно зависеть | Нельзя зависеть |
|---|---|
| `echo-protocol` (схемы + версия) | код другого слота |
| стандарт языка (JSON, HTTP) | внутренние типы runtime |
| свой вендор (Zonos, Ollama) | чужой вендор |

Кардинальная правка — это смена `echo.v1` → `echo.v2`. Тогда да, все слоты обновляют клиент протокола. Всё остальное, что хочется «чуть поменять везде», надо уметь выразить как *добавление* поля или capability, не как переименование.

## Конверт, не шина и не общие библиотеки

Каждое обращение — JSON-RPC 2.0 плюс наши поля:

```json
{
  "jsonrpc": "2.0",
  "id": "9f3c",
  "method": "tts.synthesize",
  "params": {
    "protocol": "echo.v1",
    "ctx": {
      "turn_id": "t-1",
      "speaker_id": "owner",
      "language": "ru",
      "voice_ref": { "id": "owner", "uri": "blob:sha256:…" },
      "channel": "cli"
    },
    "text": "Доброе утро"
  }
}
```

Правила конверта:

1. **`ctx` заполняет только runtime.** Слот его читает, не ходит за ним в identity.
2. **Байты не ездят в JSON.** Аудио и файлы — `BlobRef` (`uri` + `media` + частота). Слот пишет/читает блоб, в ответе отдаёт ссылку.
3. **Незнакомые поля игнорируются.** Так появляются optional-расширения без мажорной версии.
4. **На `hello` слот объявляет capabilities.** Нет `tts.stream` — runtime льёт обычный `synthesize`. Старый слот продолжает жить.

Транспорт — не часть контракта. Один и тот же конверт едет:

- по stdio (как MCP / LSP) — локально, любой язык;
- по HTTP `POST /rpc` — удалённый слот;
- позже по WebSocket, если нужен стрим.

Поменял транспорт — слот тот же. Шина (NATS/Redis) не нужна, пока один runtime на одну жизнь. Когда понадобится — слоты уже говорят конвертом, меняется только доставка.

## Методы слотов (стабильный минимум)

Общие для всех: `hello`, `probe`. Дальше — только своё.

| Слот | Методы | Не делает |
|---|---|---|
| `identity` | `resolve` | не синтезирует, не думает |
| `llm` | `complete` | не ходит в память и не вызывает тулы сам |
| `stt` | `transcribe` | не знает, кто говорит, если это не в `ctx` |
| `tts` | `synthesize` | не читает канал, не выбирает «кто я» |
| `memory` | `core`, `recall`, `remember` | не зовёт LLM «чтобы красиво записать» |
| `tools` | `list`, `call` | не форматирует ответ пользователю |
| `channel` | `deliver` + входящий `channel.turn` | не вызывает TTS сам |

Канал — единственный двусторонний слот: он **пушит** `channel.turn` в runtime и **принимает** `channel.deliver`. Остальные — request/response.

Цепочка фолбэка (Ollama → шлюз → mock) живёт **внутри слота**, не в runtime. Runtime видит один `llm`. Как слот внутри себя деградирует — его дело. Поменять порядок моделей ≠ менять протокол.

## Репозитории: как резать, чтобы не пожалеть

Отдельный репозиторий имеет смысл, когда у компонента **свой цикл жизни**: другая команда, другой язык, другой релиз. Пока это один человек, восемь гитхаб-реп без жёсткого протокола дадут только рассинхрон тегов.

Правильная нарезка такая — и её можно держать сначала пакетами в одном гите, потом вынести один в один:

```
echo-protocol     единственная общая зависимость, semver
echo-runtime      оркестратор, не знает Zonos
echo-identity
echo-llm
echo-stt
echo-tts
echo-memory
echo-tools
echo-channel
```

Внутри слота — адаптеры вендоров (`adapters/zonos`, `adapters/xtts`). Это **не** отдельные репозитории, пока второй человек не начинает жить только в Zonos.

`ECHO` (этот репозиторий) — зонт: протокол, пока что runtime, карта. Когда слот созрел — выезжает в `TimaxLacs/echo-tts` и публикует бинарь/`npx echo-tts`. Runtime в конфиге пишет `command: echo-tts`, не `import { ZonosTts }`.

Не делать: `echo-tts-zonos`, `echo-tts-xtts`, `echo-llm-ollama` как отдельные репы с первого дня. Это размножит контракт, а не изолирует его.

## Что считается кардинальной правкой

Менять другие компоненты **нужно**, только если:

- переименовали метод (`synthesize` → `speak`);
- сделали обязательным новое поле;
- сменили смысл существующего поля;
- сменили способ ссылаться на блобы.

Не кардинально (другие репы не трогаем):

- новый адаптер внутри слота;
- новый optional в `params`;
- новая capability на `hello`;
- новый канал внутри `echo-channel`;
- новая модель в цепочке `echo-llm`.

Мажор протокола — событие. Минор — «добавили, старые клиенты не видят». Патч — баг в схемах или примерах.

## Почему не «всё через MCP» и не «всё через OpenAI API»

MCP отлично закрывает **tools**. Память у тебя уже так стыкуется (`lightrag-mcp`). Голос через MCP — мучение: стрим, wav, barge-in. LLM через MCP — не его модель.

Обратная крайность: каждый слот говорит «как OpenAI». Тогда runtime становится зоопарком диалектов, и смена STT снова трогает ядро.

Поэтому слои такие:

```
вендорский API     Zonos HTTP / Ollama / Telegram
       ▲
адаптер слота      только в своём репозитории
       ▲
echo.v1            единственное, что видит runtime
```

Внутри payload можно *выглядеть* знакомо (`messages` как в OpenAI, `ToolSpec` как в MCP) — чтобы адаптер был тонким. Снаружи для runtime это всё равно `llm.complete`.

Голосовые слоты позже могут дополнительно говорить Wyoming — тогда `echo-stt` сам является мостом в экосистему Home Assistant. Runtime этого не узнает.

## Как выглядит смена одного компонента

Было:

```
runtime.slots.tts = { transport: "stdio", command: "npx", args: ["echo-tts"] }
```

Стало (другой сервер, другой язык):

```
runtime.slots.tts = { transport: "http", url: "http://192.168.1.20:5050/rpc" }
```

Конфиг runtime. Код runtime, llm, memory, channel — без диффа.

Было Zonos, стало XTTS: меняется только `echo-tts` (конфиг адаптера или бинарь). Протокол тот же: `tts.synthesize` + `BlobRef`.

## Порядок внедрения, чтобы не переписывать дважды

1. Вынести схемы в `protocol/` — это и есть будущий `echo-protocol`.
2. Перестать импортировать провайдеры из runtime: процесс или HTTP, даже если процесс пока из той же монорепы.
3. Пока слот не стабилен — пакет в этом репозитории, граница как у отдельной репы (свой `package.json`, свой README, ноль импортов соседей).
4. Вынести в GitHub-репу, когда слот умеет `hello` / `probe` / свои методы и проходит конformance из `protocol/`.

Плагины `*.mjs` в одном процессе — временный обход. Они нарушают изоляцию: общий Node, общая память, общий креш. Их место — адаптер *внутри* слота, не способ связать слоты друг с другом.

## Конformance

В `echo-protocol` лежат тесты: «на `hello` есть `protocol` и `capabilities`», «`synthesize` возвращает `BlobRef`», «лишнее поле не валит ответ». CI каждого слота гоняет этот пакет. Сломал контракт — красный слот, не красный мир.

Пока тестов мало, достаточно JSON Schema в `protocol/`. Это уже жёстче, чем TypeScript-типы, которые видит только один репозиторий.
